# design-sync notes

## Repo shape
- This is an app repo (`create-next-app` scaffold), not a publishable component-library package. `shared/ui/` (feature-sliced `shared` layer) holds the shadcn/ui-based primitives; there is no `dist/` JS build and no generated `.d.ts` — the converter runs in **synth-entry mode** (`cfg.srcDir: "shared/ui"`), scanning PascalCase exports directly from the `.tsx` sources.
- `cfg.entry` (`./dist/index.js`) intentionally points at a path that does not exist — its only job is to make the converter's package-root walk-up land on this repo's own `package.json` (name `business-management-app`). Passing no `--entry` at all would instead try `join(--node-modules, cfg.pkg)`, which doesn't resolve for an app's own repo. Do not "fix" this by creating a real `dist/index.js` unless the repo actually gets a JS library build.
- Styling: Tailwind v4, tokens + theme mapping live in `app/globals.css` (written by shadcn's `init`). There's no shipped component stylesheet to point `cssEntry` at, so `pnpm run build:ds-css` (`tailwindcss -i app/globals.css -o dist/ds-styles.css`) compiles one — it scans the whole repo for utility classes actually in use. `dist/` is gitignored (regenerated build output, like a normal package `dist/`).
- `@tailwindcss/cli` was added as a devDependency for this. `pnpm-workspace.yaml`'s `allowBuilds['@parcel/watcher']` was flipped from the create-next-app placeholder (`set this to true or false`) to `true` — pnpm's dependency-build gate otherwise makes any `pnpm run <script>` fail non-interactively (prompts for `pnpm approve-builds`).

## First-sync preview scope
- User chose: author rich previews for the 16 top-level components (Button, Input, Label, Card, Badge, Dialog, Select, Table, Separator, Textarea, Checkbox, Switch, Avatar, DropdownMenu, Tabs, Tooltip). The ~55 compound sub-parts (e.g. `CardHeader`, `DialogTrigger`, `TableRow`) ship fully functional on the floor card — not a failure, just unauthored; can be authored incrementally on a later re-sync.

## Known render warns
- `package-validate.mjs` flags 7 compound sub-parts `[RENDER_BLANK]` (root not empty, no errors, but PNG ~4.5-5KB / no visible text when rendered solo) — all outside the 16-top-level authoring scope above, and inherently context-dependent — they render as visually "nothing" without their parent structure around them:
  - `TableCell`, `TableHead`, `TableCaption` — meaningless outside a `<table>`/`<thead>`/`<tbody>` structure.
  - `DialogFooter` — empty layout wrapper with no children passed.
  - `SelectGroup`, `DropdownMenuLabel` — meaningless outside their parent menu/select context.
  - `AvatarGroupCount` — needs sibling avatars to mean anything.
  - These are triaged as legitimate/expected, not defects. Per the floor-card rule, they pass the render-check gate as-is; authoring composed previews for them (inside their parent component) is deferred to a later re-sync, not blocking this one.
- `Checkbox` also flagged `[RENDER_BLANK]` (unlabeled, no surrounding text) but is IN the 16-top-level authoring scope — not triaged here, gets fixed by authoring its preview (§4.2) this run instead.

## Re-sync risks
- No `.d.ts` contract — prop types come from ts-morph reading the raw `.tsx` source (weaker than a real declaration build). If `shared/ui` component signatures get complex (generics, cross-file type aliases), expect `[DTS_PARSE]`/`[DTS_STYLE_SYSTEM]` warnings on re-sync.
- `dist/ds-styles.css` is regenerated by content-scanning the whole repo — if a utility class is only ever used inside `app/` (not `shared/ui/`), it still gets included today because the scan isn't scoped. Not a problem yet; would only matter if `cssEntry` needs tightening for bundle size later.
- The component list is a flat scan of every exported PascalCase symbol in `shared/ui/*.tsx` — adding a new file there automatically adds new "components" (including any incidental subparts), there's no allowlist. `componentSrcMap` can exclude/pin entries later if the list gets noisy.
